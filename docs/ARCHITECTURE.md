# BugZoo 架構設計

## 第八階段的設計邊界

保留四個課程、精確規則、共用守衛、持久化、雙語與第七階段的 Chromium E2E。本階段只補充公開文件、靜態子路徑相容、品牌中繼資料與受品質守衛保護的 CI／Pages 發布；數學規則與通關條件維持不變。外部發布與 Release 的結果須以真實 API 和公開網站驗證為據。

進度與語言偏好保存在目前瀏覽器，儲存失敗時退回記憶體。沒有帳號、後端、雲端同步、追蹤、AI API 或部署。報告匯出完全在瀏覽器本地生成。

核心設計是有限的、可解釋的規則集合。機器人的「學習」表示有效示例排除了與證據不相容的候選規則，不表示訓練神經網路。相同的規則版本、有效輸入與狀態必須得到相同結果。

## 技術決策

| 選擇                          | 理由                                               |
| ----------------------------- | -------------------------------------------------- |
| React + Vite                  | 提供輕量元件開發與正式建置，不加入不需要的全端框架 |
| TypeScript Strict Mode        | 讓輸入、結果與失敗分支有明確契約                   |
| Tailwind CSS 的 Vite 整合     | 用一致的設計樣式完成響應式介面                     |
| Vitest                        | 在相同工具環境驗證精確數學、規則與教學狀態         |
| ESLint flat config + Prettier | 分別檢查程式碼品質與統一格式                       |
| pnpm + lockfile               | 固定依賴解析，支援可重現安裝                       |
| 精確有理數                    | 避免分數、折扣與機率的浮點數誤判                   |

Node.js 使用 24 LTS；套件確切版本由 `package.json` 與 `pnpm-lock.yaml` 記錄。首頁與課程使用 hash 導覽，沒有新增路由、全域狀態套件、資料庫、後端或 AI API。

TypeScript 使用 6.0 系列，與目前選用的 `typescript-eslint` 支援範圍對齊。更新工具鏈時先檢查 peer dependencies 及型別解析器相容性，再更新 lockfile 和執行完整檢查。

工具設定參考 [Vite 官方入門](https://vite.dev/guide/)、[Tailwind CSS 的 Vite 安裝方式](https://tailwindcss.com/docs/installation/using-vite)及 [typescript-eslint flat config 指南](https://typescript-eslint.io/docs/)。套件版本另外核對 npm 官方 registry 的穩定版與 peer dependencies。

## 分層與資料流

- **UI**：呈現角色、題目、結果與說明。只負責介面，不決定數學正誤。
- **課程資料**：角色介紹、教學目標、示例與課程順序。展示資料與可執行規則分離。
- **領域契約**：機器人定義、規則、實驗、驗證結果及假設狀態的 TypeScript 型別，位於 `src/domain/contracts.ts`。
- **數學工具**：純函式處理精確值與數學等值，不接觸 UI 或儲存。
- **共用遊戲狀態層**：`src/domain/teaching/engine.ts` 的純函式工廠協調教學步驟、實驗歷史、候選假設、未見題與完成條件；不依賴 React 或儲存，各機器人各自建立引擎與 session。

一次實驗的資料流如下：

```text
學生輸入
  → 領域輸入驗證
  → 正確規則計算與學生答案核對
  → 有效的教學證據
  → 各候選規則計算與精確比較
  → 更新候選假設、產生推理說明
  → UI 呈現結果
```

UI 位於 `src/app`、`src/components`、`src/features/home` 與各課程的 feature；展示資料位於 `src/content`；規則位於各自的 `src/domain/fractionFox`、`src/domain/discountPanda`、`src/domain/minusMole`、`src/domain/chanceCrow`；共用狀態與數學工具位於 `src/domain/teaching`、`src/domain/math`。

## 共用流程與領域邊界

`createTeachingEngine<Input, Answer, RuleId>` 接收現有規則契約、正確規則 ID、固定規則優先序、觀察題、輸入／答案／示例驗證、答案等值、題目等值、確定性候選題迭代器與少量文案。回傳相同的純命令；四個機器人的適配模組保留一致的公開函式名稱，UI 不需要知道工廠細節。第五階段沿用工廠與領域契約，沒有修改前三個適配。

候選一致性、猜想、有效實驗前置條件、正確答案核對、規則比較、教學紀錄、排除、三題未見選擇、依序作答、雙方正確通關及重設均只有一份流程實作。分數、折扣、整數與機率的數學規則、解析、答案型別、題目身份及候選題產生方式維持獨立。沒有動態外掛、全域可變註冊表或額外狀態套件。

`LessonProgress` 共用五步呈現；`src/components/lesson.css` 保留原有 `ff-` 類名以避免改變 FractionFox 版面，熊貓的綠色樣式由 `.dp-game` 限定。數學輸入元件與分數／價格圖分開，避免不安全地共用領域視覺。

## ChanceCrow 的精確機率與實體抽樣

`src/domain/chanceCrow/` 使用 `ChanceInput { red: bigint, blue: bigint, first: Color, second: Color }`，答案使用現有 `Rational`。每色球數為 0 至 10，總數為 2 至 12；顏色只接受 `red` 或 `blue`。球數先驗證完整整數字串，學生答案先驗證非負分子、正分母及 0 至 1 的範圍，才建立精確有理數；接受等價分數。

三條規則使用相同輸入：`correct` 計算 P(A) × P(B | A)，按第一次顏色扣除相應球數與一顆總數；`independent` 使用原始比例相乘 P(A) × P(B)；`second-only` 只使用 P(B)，混淆有順序的聯合事件與單一事件。第二次抽到 B 的無條件邊際機率確實是原始 B 比例，但它不能代替 A 然後 B 的聯合機率。若 A 不可能發生，正確聯合機率直接為零、P(B | A) 回傳未定義；不建立負球數或假的條件分數。

球袋中的每顆實體球有唯一 ID，例如 R1、R2、B1。樣本空間列舉所有不同 ID 的有序二球組合，總數 N × (N−1)，同色實體球也分開計數。符合目標顏色順序的組合數除以總組合數，應與正確規則的機率一致。矩陣的對角線表示不能再次抽到同一顆球，不列入分母。

抽樣狀態保留原袋、剩餘實體球與已抽順序。`drawBall` 使用可注入的隨機來源從剩餘球中選取並移除該 ID；第二次不可能抽到已移除球。隨機值必須有限且在 [0,1) 內。批次模擬每次重新建立原袋，在同一個二球試驗內不放回，跨試驗恢復原袋。測試注入固定數列，不依賴真實隨機運氣。

`ProbabilityLab` 用 SVG 呈現球袋、實體球及抽取動畫，並以有序矩陣呈現完整樣本空間及已抽前綴所保留的可能結果。目標理論 P(B | A) 與「實際抽到第一顆後」的剩餘比例分別標示；若實際第一顆不符合目標 A，不能把實際比例冒充目標條件。單次結果、經驗頻率與精確理論值分開呈現，經驗頻率不進入教學證據。

重播只重新呈現已取得的實體球順序，不呼叫隨機來源、不新增試驗；減少動態效果時保留即時狀態更新。更改有效組態會建立新的實驗室，無效輸入則暫停預覽並回報原因。五步遊戲重設會同時清除實驗室。驗證尚未答對的題目不呈現理論圖或可直接讀取的答案。

ChanceCrow 仍以共用工廠管理教學與完成守衛。規則優先序為 `independent → second-only → correct`；專屬驗證入口按已見歷史選出異色正機率、同色正機率與零機率各一題，保持確定性並交回共用守衛。題目身份比較解析後球數及有序目標顏色，不能靠字串補零冒充未見題。有限題型耗盡時回報不足，不重複舊題或偷偷放寬完成條件。

ChanceCrow 適配另以可選的 `additionalSeenInputs` 記錄合法題目但答案錯誤或格式不合法的教學提交，避免在驗證重複學生已看過的題目。這只改變「已見題」資訊，不新增有效證據、不縮減候選；不合法題目與錯誤階段不記錄，重設會清除。此擴充只在 ChanceCrow 的兩個適配命令中處理，沒有修改共用狀態契約或前三個課程。

## MinusMole 的整數與數線

`src/domain/minusMole/rules.ts` 使用 `SubtractionInput { a: bigint, b: bigint }` 與整數答案，三條規則為 `correct: a − b`、`subtract-absolute: a − |b|`、`absolute-result: |a − b|`。運算完全精確，不使用浮點數比較。`engine.ts` 在外部邊界檢查資料形狀、完整十進位整數格式與長度，再解析 `bigint`；運算元範圍為 −20 至 20，答案範圍為 −40 至 40。

規則優先序為 `subtract-absolute → absolute-result → correct`。教學流程仍由共用工廠執行，猜想或實驗不會自行減少候選；正確反例可以一次排除一條或兩條迷思。完成頁的有效反例數是實際淘汰至少一條規則的教學紀錄數，不把無區分能力的示例算成進展。

減法有順序，`sameSubtractionInput` 比較解析後的 a 與 b，不把交換運算元視為同一題。MinusMole 的驗證入口使用當前歷史，確定性選出正減負、負減正、負減負各一題未見候選，交回共用引擎檢查前置條件、建立驗證與判定完成；沒有第二套流程。優先題已見時依相同情境選後備題。有限範圍若某個情境已全部用過，回報題庫不足，不重複題目冒充未見題。

`numberLine.ts` 是不依賴 React 的數線模型。起點、終點、方向、距離與跨零資訊由實際規則產生，並涵蓋零位移。正確減法從 a 移動 −b；減正數向左、減負數向右。錯誤 `a − |b|` 依錯誤規則向左；錯誤 `|a − b|` 若得到負中間結果，先做真正的減法，再把負終點鏡射到正側，明示第二段是錯誤改號而非減法。

`src/features/minusMole/NumberLine.tsx` 將模型轉為原生 SVG 的箭頭、刻度、起終點與移動標記；依資料調整顯示範圍，使用稀疏刻度適配手機。座標與動畫插值可用受界限約束的 `number`，但不參與數學正誤判定。重播重新展示相同路徑，跳過立即到終點；`prefers-reduced-motion` 時直接展示完整路徑。每條線都有文字算式、方向與距離，錯誤演示和正確解釋清楚標示，避免只用顏色區分。

數線與整數輸入保留為課程專屬元件，課程共用 `LessonProgress` 與既有狀態型別。驗證作答前不呈現計算答案或數線終點，答對後才展示機器人與學生的結果。

## DiscountPanda 的精確金額與規則

金額小數字串精確解析成整數分，百分比精確解析成基點（1 基點 = 0.01%）。原價範圍為 0 到 1,000,000.00 元；兩個折扣各為 0% 到 100%。不接受負值、超界、超過兩位小數、科學記號或缺少欄位。

正確規則為 `priceCents × (10000 − firstDiscount) × (10000 − secondDiscount) / 100000000`。中間值保持精確有理數，只在最終結果採 half-up 四捨五入到整數分。迷思 A 先將折扣加總封頂至 10000 基點，再扣除原價；迷思 B 只套用第二折扣。所有規則得到非負價格。

驗證與證據比較使用最終捨入後的整數分。若不同規則的精確結果在分精度下相同，示例有效但不能排除那些規則；圖上的比例與中間價格不回流成判斷依據。介面明示捨入政策，價格階梯使用精確領域資料呈現。

折扣題目的身份以解析後的原價及折扣組合比較，不能透過 `100` 改寫成 `100.00` 產生「未見題」。保守地把交換兩次折扣也視為相同題目，避免藉交換順序宣稱遷移。具體題庫與價格範圍由 DiscountPanda 適配提供，共用引擎負責排除觀察、實驗、有效教學及本次已選題目。

FractionFox 的主要檔案為：

- `rules.ts`：三條精確規則、`AdditionInput`、`RuleId` 與推理步驟。
- `engine.ts`：外部字串輸入驗證、`fractionFoxDefinition`、題目等值與候選題提供；使用共用工廠並維持原有狀態型別及命令介面。
- `engine.test.ts`：規則、驗證與狀態行為的測試。
- `FractionFoxGame.tsx`：React 畫面與事件，將使用者輸入交給領域命令。
- `FractionFields.tsx`、`FractionVisual.tsx`：文字輸入與分數呈現；沒有第二份規則判斷。

UI 文案中的角色名稱不能作為引擎查找鍵；穩定 ID 用於識別，顯示名稱可以在後續加入翻譯。

## 機器人與規則契約

`src/domain/contracts.ts` 目前定義以下最小契約：

| 型別                                  | 職責                                                 |
| ------------------------------------- | ---------------------------------------------------- |
| `RobotDefinition<Input, Answer>`      | 穩定 ID、文案鍵、領域、一個正確規則及候選迷思規則    |
| `ReasoningRule<Input, Answer, Kind>`  | 規則 ID、正確或迷思類別、描述鍵與純函式 `evaluate`   |
| `RuleEvaluation<Answer>`              | 答案與使用說明鍵的推理步驟                           |
| `ExperimentSubmission<Input, Answer>` | 實驗輸入及學生主張的 `proposedAnswer`                |
| `ExperimentDomain<Input, Answer>`     | 從 `unknown` 驗證提交內容，並提供精確 `answersEqual` |
| `ValidationResult<Value>`             | `ok` 判別的成功值或驗證問題集合                      |
| `HypothesisState`                     | 仍存活的 `remainingRuleIds`                          |
| `LessonDefinition`                    | 課程 ID、角色 ID、標題與學習目標鍵，不包含規則狀態   |

學科的限制由領域驗證管理，主題與教學目標由課程資料管理，初始候選假設由遊戲狀態層建立。課程介紹、圖像與頁面樣式放在展示資料，不放入數學判斷。

同一機器人的正確與錯誤規則使用相同的輸入、輸出契約；差異在於規則本身的推理方式。規則包含穩定 ID、名稱、正確或迷思類別，以及可回傳答案和解釋步驟的純函式介面。規則計算不能修改假設狀態，也不能隱含讀取隨機數或時間。

正確規則是驗證學生答案的基準。錯誤規則是具體、可重現的迷思。FractionFox 使用三個規則：

| 規則               | 對 `a/b + c/d` 的答案 |
| ------------------ | --------------------- |
| 正確通分           | `(a×d + c×b)/(b×d)`   |
| 分子、分母各自相加 | `(a+c)/(b+d)`         |
| 保留第一個分母     | `(a+c)/b`             |

這些規則只適用於本階段的分數加法課程；不將它們視為其他機器人的實作。

學生提交的實驗包含輸入和主張的正確答案。提交內容在驗證前是外部資料，不能因 TypeScript 的靜態型別就假定有效。驗證結果必須區分可接受的證據與具體錯誤，以利 UI 呈現原因及測試檢查。

## 實驗驗證與假設淘汰

實驗分兩個檢查步驟：

1. **輸入有效性**：檢查資料形狀、數值及領域限制，例如分母不能為零、折扣範圍合法、抽樣數不能超過物品總數。
2. **答案正確性**：執行正確規則，以領域的精確等值函式核對學生答案。只有通過此步驟的實驗才建立教學證據。

FractionFox 的 `parseAddition` 和 `parseAnswer` 接收 `unknown`，確認物件及整數字串後才建立領域值。輸入可有正負號並會去除前後空白，但不接受小數、科學記號或超長字串。題目分子的絕對值至多 1000，分母必須為 1 至 1000；學生答案採獨立的上限，分子絕對值至多 1,000,000,000,000、分母為 1 至 1,000,000,000,000。這能接受 `1/1000 + 1/999 = 1999/999000` 等合法答案及合理的未約分等值形式。

`runExperiment` 記錄目前機器人與正確規則的預測，但不排除候選。只有 `teachExample` 接收 `{ input, proposedAnswer }`、確認答案正確後，才保存 `TeachingRecord` 與更新假設。教學記錄包含每條候選的預測、相容性、排除及剩餘 ID，避免 UI 自行推測更新理由。

尚未驗證的學生主張不能排除任何規則。驗證失敗時保留現有假設，回傳原因讓學生修改實驗。

對每一條仍存活的候選規則，使用有效實驗的相同輸入計算結果，再與已驗證答案比較。只排除答案不相容的候選；保留相容規則與排除理由，讓學生看到證據如何影響機器人。

- 若正確與錯誤規則恰好得到相同答案，示例仍有效，但不能區分這些假設；引導學生設計更有辨識力的反例。
- 若仍有多條相容規則，狀態保持未確定，不能宣稱已學會。
- 若只剩正確規則，表示它是目前唯一相容的候選；四個課程仍須完成三題未見題驗證才可標記完成。這不是對所有可能推理方式的保證。
- 若候選集合意外變為空，回報規則或證據的一致性錯誤；不能靜默選擇正確答案、補入規則或宣稱完成。
- 已排除規則與實驗歷史應能追溯；重新開始課程時才能明確重置狀態。

將正確規則保留在初始候選集合中，使合法的正確示例理應至少保留該規則。候選集合與機器人正在展示的推理規則是兩個概念：機器人可以起初展示迷思規則，但不代表正確規則不能成為學習候選。

FractionFox 的規則優先序為 `add-both` → `keep-first` → `correct`；DiscountPanda 為 `add-discounts` → `only-second` → `correct`。共用引擎選擇第一個仍存活的規則，使相同的有效示例序列得到相同推理與更新；沒有隨機切換或模擬模型訓練。

## 五步教學狀態與完成守衛

`SessionState` 的流程為 `observe → hypothesize → experiment → teach → verify → complete`：五個教學活動完成後進入成果頁。

| 狀態          | 主要命令與條件                                                                          |
| ------------- | --------------------------------------------------------------------------------------- |
| `observe`     | `beginHypothesis` 進入猜想                                                              |
| `hypothesize` | `chooseHypothesis` 保存猜想並進入實驗，不淘汰候選                                       |
| `experiment`  | `runExperiment` 保存有效實驗；`beginTeaching` 要求已選猜想且至少有一個有效實驗          |
| `teach`       | `teachExample` 建立有效證據；`beginVerification` 要求只剩正確規則及已有實驗、猜想、證據 |
| `verify`      | `answerVerification` 依序接受三題正確答案，並重新核對機器人答案                         |
| `complete`    | 只有領域完成條件通過後到達；`resetSession` 可重新建立初始狀態                           |

命令回傳 `SessionResult`，包含下一個狀態與 `Feedback`。錯誤步驟、無效輸入、錯誤示例、候選一致性問題或錯誤驗證答案都回傳原因並保留原狀態。React 依結果更新 UI；按鈕是否啟用只是提示，不能替代領域守衛。

FractionFox 提供固定順序的合法單位分數組合，`sameAddition` 以精確等值檢查加數並排除互換。DiscountPanda 提供不同價格與小數折扣的優先候選，再提供確定性後備題池，`sameDiscountInput` 排除相同價格與折扣交換。共用引擎排除觀察題、所有有效實驗、已接受的教學示例及本次已選的驗證題。「未見」是領域定義的題目等值，並非字串不同。

驗證依序進行，答錯不計入且可重試。完成時必須同時滿足只剩正確候選、三個學生答案都正確，以及機器人依目前規則計算三題都正確。三題只檢驗本課程與已知候選集合；它不是對本課程全部題型或所有未知推理方式的學習保證。

共用 `resetSession` 清除候選更新、猜想、實驗、教學證據與驗證結果，回到各課程的三條候選與初始迷思：FractionFox 為 `add-both`，DiscountPanda 為 `add-discounts`，MinusMole 為 `subtract-absolute`，ChanceCrow 為 `independent`。第六階段 UI 訂閱本地 store，返回首頁再進入會恢復進度；只有明確確認的重設才清除課程。表單、動畫與實驗室瞬時狀態在掛載時安全初始化。

## 避免浮點數誤差

分數、有限小數、百分比與機率使用有理數 `numerator / denominator`，分子與分母採 `bigint`。基礎工具將分數約分、將分母符號固定為正，並拒絕零分母；等值判斷依精確整數運算完成。

FractionFox 將題目的原始分子與分母和答案的規範化有理數分開。若先把題目約分，`2/4 + 2/4` 會變成 `1/2 + 1/2`，迷思規則的實際推理也跟著改變。規則因此讀取原始整數項，只有答案建立及等值比較使用約分；學生提交的等值答案仍可接受。

DiscountPanda 的小數先依字串精確解析，不先轉成 JavaScript `number`。分數與其他未來領域的有限小數也應採相同原則。顯示用的圖形比例不得回流作為正誤判斷依據；金額的捨入規則由課程明確定義。

`bigint` 不能直接序列化成 JSON。第六階段 codec 使用十進位字串表示整數，例如 `{ "numerator": "1", "denominator": "4" }`，並在讀取邊界驗證字串、限制輸入大小與用既有領域解析器還原。FractionFox 運算元保留未約分表示。

有理數不是所有學科的通用答案格式。未來涉及集合、文字或非有理數時，各領域自訂答案型別及等值策略；不得為了共用介面而退回浮點數或字串比較。

## 新增機器人或學科

新增角色時，先定義教學目標和具體迷思，再提供輸入驗證、正確規則、有限候選規則與答案等值函式。使用既有領域契約，將課程描述留在資料層，將角色顯示留在 UI。

針對新領域建立正確示例、能區分迷思的反例及無效輸入測試。只有在第二個實際領域提出共同需求時再抽取共用行為；不預建動態外掛註冊、遠端執行或任意程式碼載入機制。

翻譯與保存是呈現及外部資料邊界，不進入核心數學判定。新增課程或修改規則時同步維護翻譯、codec 適配及課程版本，避免把舊證據直接套用於新規則。

## 本地進度與重播恢復

`src/progress/types.ts` 描述四種明確的課程狀態映射、儲存介面及摘要；`codec.ts` 是不依賴瀏覽器的精確 JSON 邊界；`store.ts` 管理獨立鍵與記憶體後備；`hooks.ts` 用 `useSyncExternalStore` 讓課程、導覽及報告同步訂閱。

每課程鍵為 `bugzoo.progress.<lessonId>`。DTO 包含 `schemaVersion: 1`、`lessonVersion: 1`、課程 ID、階段、猜想、有效實驗輸入、已接受的教學輸入／答案、依序接受的驗證答案。ChanceCrow 另保存合法但答案被拒絕的額外已見題，以維持未見題語意。候選、機器人目前規則、答案比較、題庫、統計與通關旗標都不保存。

分數及機率的分子／分母、整數皆為十進位字串；金額及百分比由既有精確格式化函式輸出，再由原解析器還原整數分／基點。FractionFox 的運算元保持原始未約分表示。沒有通用 `bigint` replacer，也不將整數轉成 JavaScript 浮點數。

讀取先限制 JSON 文字長度（128,000 字元）、欄位形狀及數值字串長度，再限制每類歷史最多 100 筆、驗證最多三筆。只接受已知欄位、已知課程、明確版本與合法步驟。按照 `beginHypothesis → chooseHypothesis → runExperiment → beginTeaching → teachExample → beginVerification → answerVerification` 重播，每一步須通過既有領域驗證。由同一批已見題確定性重建驗證題，僅接受按順序答對的答案；最後階段必須與重播結果相同。因此直接添加 `complete`、候選或假通關旗標都無效。此機制驗證數學與流程一致性，不提供防止使用者自行製作完整正確學習紀錄的身分認證。

首次加入儲存功能，沒有已發布舊格式可安全遷移。`lessonVersions` 為四課分別指定版本，目前皆為 1；單一課程規則變更時只更新自己的版本。未知 schema 或課程版本標示 `unsupported-version`，損壞資料標示 `corrupt`，只令受影響課程回到安全初始狀態。第七階段以內部 rejected-record 集合保留原文字，只有明確重設才允許覆寫；新的有效操作可以在記憶體繼續，不能假裝已安全遷移。成功讀取其他分頁更新的有效資料或刪除事件會解除過時的拒絕狀態。未來若有具體相容舊格式，加入小型版本轉換後仍須走相同重播驗證。

每次有效狀態更新立即寫入自己的鍵。Storage getter／讀取／寫入／刪除都可失敗；失敗或超過保存上限時保留新的記憶體狀態，標示 `memory-only`，不影響數學或阻擋繼續學習。刪除失敗時明確提醒舊的持久紀錄可能於重開後恢復。`resetLesson` 只移除一課程，`resetAll` 只移除四個已知進度鍵，保留語言及其他網站資料；UI 先要求確認。其他分頁的 storage 事件會更新受影響摘要。

SSR 提供四個真正的初始摘要且不存取 LocalStorage；瀏覽器訂閱使用穩定快照，避免重複初始化與渲染迴圈。有效教學與驗證保存；表單草稿、數線播放位置、抽球瞬時結果與模擬頻率不保存。恢復不呼叫 RNG，ChanceCrow 的實驗室安全建立新球袋，教學證據仍保留。

## 雙語呈現與語言偏好

`src/i18n/` 提供 `Locale`、受型別約束的 `MessageKey`、翻譯函式、動態插值及 React provider。已存在的繁體中文短句作為來源 key；英文字典按首頁及課程分檔，有限的動態推理／錯誤文案由已知訊息與變數對應。缺失內容回退來源文案，數學規則與結果不受語言影響。新增可見文字、表單驗證、推理與無障礙標籤時須補上字典與翻譯測試。

全站導覽控制獨立的語言 store，`bugzoo.locale.v1` 只保存 `zh-TW` 或 `en`，其餘值回到預設繁體中文。切換即時更新文案及 HTML `lang`，不更換課程 key、不重建 session。語言保存失敗仍可切換當次頁面；進度清除不觸及此鍵。Dashboard／Passport 的集中型別字典描述各自報告文案，避免在元件內重複語言分支。

## Dashboard、Passport 與本地隱私

`src/features/progress/` 從 store 摘要計算已完成、進行中、有效反例及驗證完成數。有效反例是確實淘汰至少一條規則的教學紀錄，不把無區分示例、錯誤答案或模擬次數算成教學進展。每課程卡片提供真實階段、SVG 角色與繼續／成果入口。

學習護照列出實際已排除迷思、有效反例、驗證結果及概念回顧。只有完成且三題皆通過的紀錄取得原創 SVG 徽章；文案明確限制為完成遊戲挑戰，不能宣稱已證明現實學科能力。純 `createLearningMarkdown(summaries, locale, date)` 生成本地報告內容，瀏覽器邊界使用 Blob／object URL 下載並釋放 URL，沒有網路呼叫、文件服務或 PDF 依賴。

學習資料僅在目前瀏覽器，不需要帳號、不收集個人識別資訊、不上傳、不支援跨裝置同步。清除瀏覽器資料可能遺失進度。單一／全部重設後，訂閱者同步重新呈現狀態、統計及成就。

`ConfirmationDialog` 共用原生 HTML `<dialog>` 的模態及鍵盤行為。開啟時只描述即將執行的清除，聚焦取消；Escape／取消不改變 session 或草稿，確認才呼叫 store 重設，關閉後返回原焦點。第七階段 E2E 發現原生 Tab 行為會移離內容，因此在兩個操作按鈕的 Tab／Shift+Tab 邊界明確循環焦點。沒有使用阻塞 JavaScript 的 `window.confirm`，不新增對話框套件。

## 第七階段的呈現及載入邊界

四課程、Dashboard 與 Passport 使用 `React.lazy`，首頁維持同步可用。共用精確引擎、codec、store 與語言字典仍是單一資料來源，不為分割程式碼重建規則。`Suspense` 提供雙語載入狀態，路由錯誤邊界提供重新載入操作；hash 決定頁面身份，語言切換不改變 key 或 session。

使用者導覽後，課程依既有步驟焦點管理；非課程頁面在載入完成後聚焦 main。全站提供略過導覽入口。首頁及角色課程入口樣式移至全域 CSS，防止首次載入借用尚未下載的課程樣式。

`fieldFeedback.ts` 僅把領域錯誤路徑對應到 UI 的錯誤 ID，不參與正誤判斷。欄位保留提示文字關聯，再加上錯誤關聯；編輯後移除過時錯誤。數線與球袋仍由既有純模型驅動，保留文字替代資訊及 reduced-motion 分支。

球數上限 12 使有序結果最多 132 個；保留完整空間有教學價值，沒有增加虛擬化框架。表格最低每欄 28px、字級 11px，置於可聚焦且具名稱的水平捲動區，避免以 6–7px 字體塞進手機。

## 自動化瀏覽器邊界

`playwright.config.ts` 使用 [官方 webServer 設定](https://playwright.dev/docs/test-webserver) 自動啟動獨立本機 Vite 4173，結束後停止；不重用未知伺服器。16 個高價值案例分別在 Chromium 1280px 與 320px 執行，重試為零。預設使用 Playwright Chromium；可明確指定既有 Chrome／Edge channel，實測使用 Chrome 155.0.8059.40。

`e2e/fixtures.ts` 使用每測試獨立 context，語言僅在沒有偏好時初始化；監看所有新舊分頁的瀏覽器錯誤、警告及非本機請求。有效進度由 UI 產生；損壞／版本測試才直接修改儲存。教學答案及驗證答案依畫面資訊、獨立精確運算與真實提交判定，不注入成功旗標。

Vitest 驗證純數學、命令與外部資料邊界；Playwright 驗證真正的使用者流程、恢復、語言、下載、對話框、焦點、reduced motion 與頁面寬度。兩者互補。trace、截圖與 HTML 報告列入忽略；沒有增加測試產物到產品資源或正式 JavaScript。

## 可測試性

領域及數學層保持純函式，讓測試不用啟動瀏覽器即可驗證。第七階段保留原有 348 個測試，新增 5 個欄位回饋及 2 個拒絕紀錄保留測試；E2E 獨立補充四課程及瀏覽器流程。不改動數學或通關預期。

型別與單元測試不能取代瀏覽器流程驗證；交付前仍需在桌面及手機檢查四個首頁入口、完整五步流程、錯誤回饋、重設、鍵盤操作與 console，以及實體球移除、同色與異色、零事件、樣本空間與重播。當次執行命令及結果記錄於 README，不能以舊階段紀錄替代當次驗證。

## 第八階段的靜態部署與發布

`src/deployment/basePath.ts` 驗證 `BUGZOO_BASE_PATH`；開發預設 `/`，正式專案 Pages 使用真實倉庫子路徑。拒絕 URL、traversal、編碼分隔字元及缺失的尾斜線，不能將外部地址當成靜態 base。首頁 Logo、favicon 及 Open Graph PNG 使用 Vite BASE_URL；動態 UI 的 JS／CSS 由 Vite 同一個 base 產生，hash 深連結在刷新時仍請求靜態 index。

`src/i18n/pageMetadata.ts` 依已知路由與語言產生 title、description 及 Open Graph 語系。Provider 只同步 document 中繼資料，不更改 session、規則或答案。品牌 PNG 從原創可編輯 SVG 產生，尺寸 1200 × 630；沒有加入外部素材或字型。

Playwright 延伸原有案例，可用 `BUGZOO_E2E_BASE_URL` 指定真實前綴，`BUGZOO_E2E_PRODUCTION=1` 自動 preview 已建置的 dist，或 `BUGZOO_E2E_EXTERNAL=1` 操作真正的公開網站。監看來源依真實 origin 決定，HTTP 失敗亦會令驗收失敗，不能忽略資源 404。新發布案例核對實際圖片格式、PNG 尺寸、路由刷新、雙語 title 與未知 hash 回退。

`quality-and-pages.yml` 在 main／PR 執行相同工程守衛與 production Chromium E2E。main 的成功品質工作只上傳 dist，部署工作 needs 品質工作且只在 main 執行；使用官方 Pages artifact／OIDC，沒有私人部署 Token 或 continue-on-error。base 由實際 repository 決定，再與官方 Pages metadata 比對；相異時拒絕部署。最小權限、部署 concurrency、frozen lockfile 與原有測試不可移除。

來源公開前檢查與素材範圍見 ASSETS，發布及線上驗證記錄見 DEPLOYMENT。學習資料仍只存於瀏覽器；正常網站資源請求會送至託管服務，不能將「沒有上傳學習紀錄」寫成「網站沒有任何網路請求」。
